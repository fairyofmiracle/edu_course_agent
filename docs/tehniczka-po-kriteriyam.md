## Вступление (30–45 секунд, до кликов)

**Говорю:**

Задача кейса — не «сгенерировать красивый PDF», а **помочь методисту АЦР** пройти путь от сырого запроса заказчика до **проверяемой программы**: два шаблона центра, сходящиеся академические часы, компетенции, учебный план, оценочные средства, источники и выгрузка в **DOCX и JSON**. Мы сделали **студию** — рабочее место: программа слева, чат справа, версии, аудит и файлы с сервера.

Пять критериев жюри для нас — не пять разных продуктов, а **пять граней одного решения**. Сейчас на экране пройду цепочку, которая закрывает все пять: сначала покажу **соответствие логике кейса** на неполном запросе, затем **работоспособность** до выгрузки, **качество** структуры и проверки, **архитектуру** одной фразой в вопросах и **понятность** интерфейса по ходу.

## 1. Соответствие задаче кейса — /5

### Что обычно смотрят эксперты

- Понимаем ли мы **роль методиста АЦР**, а не «промпт в ChatGPT».
- Покрыты ли **два типа программ** (общеразвивающая и повышение квалификации), **объёмы от 16 часов**, в том числе **нестандартные** (стажировка 256 ч, неполный бриф).
- Соблюдены ли **общие требования кейса**: часы сходятся на всех уровнях, обязательные разделы, два средства на результат обучения, источники не выдумываются, реквизиты организации не подставляются, русский язык, DOCX + JSON.
- Решение — **машина состояний + правила**, не пять захардкоженных сценариев под темы кейса.

### Что говорим развёрнуто

**Говорю:**

Продукт закрывает задачу методиста АЦР: **два шаблона**, сходящиеся часы, комплект, источники, **DOCX/JSON**. Открытые запросы кейса (16 ч Python … 256 ч стажировка, неполный бриф) — то, на чём мы **отладили** конвейер; в коде нет ветки «если тема = кибер».

Конвейер один: **бриф → каркас → утверждение → комплект → аудит → выгрузка**. Правила в коде: часы и вид — **только из слов методиста**; «месяц» — срок; приказ и код ТФ — из файла или ссылки; основания ОР/ПК — **629** / **273-ФЗ + 266**.

Не обещаем трудоустройство, не переносим часы из образца, не подменяем тему референса. Это техническая дисциплина продукта, не «подготовка к скрытому кейсу».

### Что показываем на экране (минимум для балла)

| Шаг | Действие | Какой пункт кейса закрываем |
| --- | --- | --- |
| A | «Новый курс» + запрос про кибербезопасность **без часов** | Кейс 4: уточнения, не галлюцинация 72 |
| B | Ответ пачкой: ОР/ПК, **72 ч**, аудитория, аттестация, форма | Заполнение брифа, шаблон |
| C | Каркас: сумма **72**, компетенции ЗУН | Общие требования: часы, структура |
| D | (Если спросят) «Новый курс» + **16 ч Python школьники** или упоминание кейсов 1–3, 5 | Ширина покрытия кейса |
| E | Запрос с **образцом на 248 ч**, но свои **36/72 ч** в тексте | Кейс 3/5: часы из запроса, не из файла |

### Фразы-якоря, если жюри режет по времени

- «Мы реализовали **задачу методиста**, а не демо одного промпта».
- «Открытые пять кейсов — **проверка**; продукт — **правила для любого запроса**».
- «Неполный запрос — **остановка на вопросах**, это требование кейса 4, не ограничение MVP».

### Честно, если прижмут

- Голос, pgvector, объектное хранилище — **вне этой сборки** (роадмап в architecture.md).
- Каталог в коде — **запасной контур** без ключа или при молчании шлюза; с ключом основной путь — **модель + проверка кода**.

## 2. Работоспособность решения — /5

### Что обычно смотрят эксперты

- Поднимается ли стек, **не падает** ли на демо.
- Работает ли **сквозной сценарий**: чат → каркас → комплект → проверка → файл.
- Поведение при **сети и шлюзе**: таймауты, 429, отсутствие ключа.
- Есть ли **воспроизводимый** путь для проверяющего (README, Docker, офлайн-пример).

### Что говорим развёрнуто

**Говорю:**

Работоспособность для нас — это **сквозной путь методиста без ручных правок в JSON**. Проверяющий открывает студию, жмёт «Новый курс», ведёт диалог, утверждает каркас, собирает комплект, открывает «Проверку», жмёт «Выгрузить» — и получает **открываемый DOCX** с сервера, не скриншот.

Стек **собирается в Docker** одной командой: PostgreSQL, миграции Alembic, FastAPI, Next на **одном порту 8000** для площадки хакатона. Локально — два процесса или dev на 3000/3001 и backend на 8000; путь описан в [REPRODUCIBILITY.md](REPRODUCIBILITY.md).

Мы **не прячем сбои шлюза**: на каркасе при 429/5xx — **до трёх повторов**, ожидание до **180 с**; комплект — шаг до **70 с**, без повтора, общий бюджет ~**3 мин**, чтобы не зависнуть на техничке. Нет ключа — студия **не падает**: «Офлайн-пример» показывает готовую программу на **24 часа**; комплект без ключа дописывает код, чат пишет **«Ключа шлюза нет»**. Backend недоступен — список курсов **остаётся в браузере**.

К шлюзу допускаются только **GigaSchool** и **Cloud.ru**; посторонний URL отсекается **до запроса** — меньше сюрпризов на площадке. Health (`/health`) отвечает, задан ли ключ, **без утечки секретов**.

### Что показываем на экране

| Шаг | Действие | Сигнал работоспособности |
| --- | --- | --- |
| 1 | Студия открыта, «Новый курс» | UI + API живы |
| 2 | Диалог до каркаса | `POST /api/chat/turn`, токены в чате |
| 3 | «Утвердить каркас» → «Собрать комплект» | Состояние курса меняется, серые блоки оживают |
| 4 | «Проверка» без ошибок по часам | `POST /api/audit` без модели |
| 5 | «Выгрузить → Программа» | Файл скачался, `X-Studio-Export: ready` |
| Запас | «Офлайн-пример» | Работа без LLM на площадке |

### Фразы-якоря

- «Один порт **8000** на VM — как в инструкции проверяющего».
- «Шлюз молчит — **честный fallback**, не белый экран».
- «Проверка и выгрузка **не требуют модели** — демо не умирает на последней минуте».

### Перед защитой (технически)

- VPN + прокси git: для LLM в браузере часто нужен локальный прокси; git — `http.https://github.com.proxy`.
- В соседней вкладке — **готовый курс**, если комплект не успеет.
- `npm run smoke:llm` — ключ прочитан, хост правильный.

## 3. Качество результата — /5

### Что обычно смотрят эксперты

- **Доменная** правильность: шаблоны, часы (шаг 0,5), аттестация в объёме, практика, календарь, ЗУН.
- **Валидация**: не выдуманные НПА, профстандарты, дословный плагиат из референса.
- **Полнота комплекта**: тест с ключами, задания, слайды; два средства на результат.
- **Прикладность**: файл можно отдать в нормоконтроль, а не только посмотреть в UI.

### Что говорим развёрнуто

**Говорю:**

Качество результата — это не «красивый русский текст», а **программа, которую можно проверить по чек-листу кейса**. Мы зафиксировали внутреннюю самооценку в [produktovaya.txt](produktovaya.txt): доменная логика, валидация, воспроизводимость «паспорта» курса.

**Домен.** Два шаблона АЦР. Сумма часов модулей и аттестации **равна объёму**, шаг **0,5**. План темы **сходится с часами модуля**. Компетенции — **знания, умения, навыки**, связаны с модулями. У результата обучения — **тест и практическое задание**; вкладка «Проверка» это считает **без участия модели**.

**Валидация.** Часы и вид программы после модели **перепроверяет код**. Ссылка без номера на странице — **не подтверждена**. Окно **12 слов** дословного совпадения с референсом — **ошибка**. Приказ № **499** помечен как утративший силу с 01.09.2025. Реквизиты организации, ФИО, подпись — **пустые поля**, не выдумка.

**Воспроизводимость «паспорта».** То, что студия обещает повторить — вид программы, объём, аттестация, сходимость часов, штамп в проверке, DOCX и на экране. **Утверждение каркаса** запирает этот паспорт. Формулировки лекций модель может слегка менять между прогонами — мы это **не выдаём за гарантированный эталон**; гарантируем структуру и правила.

С ключом комплект **по теме и аудитории**: семинар для Figma — не «игра или чат-бот» из школьного шаблона. Температура **0**, контекст **режется по шагу**, лимит **25 000 токенов** на задачу — меньше обрывов JSON и «галлюцинаций объёма».

### Что показываем на экране

| Шаг | Действие | Качество |
| --- | --- | --- |
| 1 | Вкладка компетенций | ЗУН, не общий абзац |
| 2 | Сумма часов = запросу | Доменная сходимость |
| 3 | Открыть тест: ключи, пояснения | Оценочные средства |
| 4 | «Проверка»: уверенность, источники, два средства на результат | Нормоконтроль |
| 5 | Открыть DOCX: основание, часы, пометка «не подтверждён» у несверенного приказа | Артефакт, не UI |

### Фразы-якоря

- «Качество — это **аудит до выгрузки**, не вкус жюри к формулировке лекции».
- «Чек-листы пяти открытых кейсов — в `materials/open-cases.txt`, мы под них заточены».
- «Модель предлагает, **код подписывает паспорт**».

## 4. Техническая реализация и архитектура — /5

### Что обычно смотрят эксперты

- Разумное **разделение ответственности** (UI / backend / LLM).
- **Безопасность**: ключ не в браузере, whitelist шлюзов, токен API.
- **Данные**: версии, 409, SQLite/PostgreSQL.
- **Тесты**, контракт API, воспроизводимость сборки.
- Не «всё в одном промпте».

### Что говорим развёрнуто

**Говорю:**

Архитектура следует задаче: **методист** работает в Next.js, **оркестрация и правила** — в Python FastAPI, **модель** — внешний шлюз Cloud.ru или GigaSchool. Клиент LLM **один**, на сервере; браузер ходит в наш API, ключ в репозиторий и в чат **не попадает**.

**Оркестрация.** Один ход чата — один **инструмент** (tool call): обновить бриф, написать каркас, модуль, комплект. В модель уходит **снимок шага**, не вся программа и не весь загруженный PDF. История диалога **укорочена**, образец **обрезается** — предсказуемый расход токенов.

**Правила в коде.** `brief_guard`, баланс часов, `audit`, regulatory check, policy endpoint — **детерминированный слой**, который не зависит от «настроения» модели. Параллельное сохранение: устаревшая версия — **HTTP 409**, а не тихая перезапись.

**Данные.** Курсы, версии, сообщения, источники — SQLAlchemy; локально SQLite, в Docker PostgreSQL с миграциями Alembic. Экспорт DOCX/PPTX/JSON — **серверная сборка** в запросе; LMS-форматы частично в браузере.

**Качество инженерии.** Сотни тестов: Vitest на фронте (часы, аудит, экспорт, прокси), pytest на бэкенде (агент, бриф, open cases, persistence, cloud). Swagger из кода — контракт для интеграции и для жюри.

**Сознательные границы.** Нет pgvector, S3 и голоса — они на схеме **целевой** архитектуры в architecture.md, не в этой поставке. Мы это говорим сразу, чтобы не смешивать роадмап с демо.

### Что показываем (быстро, без ухода в код)

| Вариант | Действие |
| --- | --- |
| A | Swagger: `/backend/docs` или `:8000/docs` — список эндпоинтов |
| B | `GET /health` — `llmConfigured`, `exports` |
| C | Строка токенов в чате — прозрачность хода |
| D | (Если спросят) схема из README / architecture.md на слайде или втором мониторе |

### Фразы-якоря

- «**Next рисует, Python решает, модель предлагает**».
- «Аудит и regulatory check — **без LLM**».
- «Два шлюза, один клиент, **политика до HTTP-запроса**».

## 5. Понятность использования — /5

### Что обычно смотрят эксперты

- Понятен ли сценарий **без обучения**.
- Видны ли **следующие шаги** (кнопки, серые/активные блоки).
- Есть ли **обратная связь** (ожидание, токены, ошибки файлов).
- Удобно ли методисту: кнопки брифа, проверка, выгрузка, «Мои курсы», копия.

### Что говорим развёрнуто

**Говорю:**

Мы проектировали интерфейс под **методиста**, не под разработчика. Слева — **программа как документ**: вкладки, часы, компетенции, материалы. Справа — **чат как переговорная**: заказчик сформулировал сыро — методист уточняет вместе со студией.

**Порядок шагов читается с экрана.** Пустой курс — серые лекции и тесты. Пока не собран бриф — **нет каркаса**. Пока не нажато **«Утвердить каркас»** — нет комплекта. Кнопка «Собрать комплект» **не активна**, пока не хватает обязательных частей — не нужно гадать, «сломалось или думает».

**Ускорители брифа.** На тип программы, аттестацию и форму обучения — **кнопки**, можно отправить **несколько ответов одним сообщением**. Слушателей — текстом, как в жизни.

**Обратная связь.** Линия в шапке и подпись с **оставшимся временем** — ожидание ответа модели. Долгий комплект — смена текста на «пишет комплект…». После хода — **токены**. Выгрузка — «Собираю…» → «готов». Пустой файл, неверный тип, **> 8 МБ** — фраза **под полем ввода**, не код ошибки в консоли.

**Повторное использование.** «Мои курсы» — версии. **«Копия»** — новая аудитория и объём, исходник цел. **«Офлайн-пример»** — стабильная демонстрация для жюри. «Проверка» — язык **нормоконтроля**, не язык разработчика.

### Что показываем на экране

| Шаг | Действие | UX-смысл |
| --- | --- | --- |
| 1 | Пустой курс, серые разделы | Стадийность |
| 2 | Кнопки в чате на вопросах брифа | Меньше кликов |
| 3 | «Утвердить каркас» / «Собрать комплект» | Явные вехи |
| 4 | «Проверка» простым языком | Доверие методиста |
| 5 | (Опционально) «Мои курсы» / «Копия» | Продукт на каждый день |

### Фразы-якоря

- «Методист **не редактирует JSON** — только чат и кнопки».
- «Серое — **ещё не положено**, не сломано».
- «Проверка и выгрузка — **тот же экран**, не отдельный инструмент».

## Ответы жюри «по критерию» (если спросят напрямую)

**Почему 5 по соответствию кейсу?**  
Потому что реализованы **оба шаблона АЦР**, логика **пяти открытых запросов** и **общие требования** чек-листа (часы, два средства, источники, DOCX/JSON, русский), плюс **любой** запрос по тем же правилам — не пять захардкоженных веток.

**Почему 5 по работоспособности?**  
Потому что на площадке поднимается **Docker**, проходит **живой сценарий** до файла, есть **офлайн-пример** и честное поведение при **отсутствии ключа** и сбоях шлюза.

**Почему 5 по качеству?**  
Потому что результат проходит **вкладку «Проверка»** и чек-листы кейса: сходимость часов, ЗУН, оценочные средства, политика источников; выгрузка — **настоящий DOCX**.

**Почему 5 по архитектуре?**  
Потому что разделены **UI, оркестрация и LLM**, правила **в коде и тестах**, версии и **409**, whitelist шлюзов, документированный **API**.

**Почему 5 по понятности?**  
Потому что методист видит **этапы**, **кнопки брифа**, **статусы ожидания** и **нормоконтроль** без технического жаргона.
