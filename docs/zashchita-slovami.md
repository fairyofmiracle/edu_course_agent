## 0. Продать красиво — 40 секунд на старте

**Говорю (коротко, уверенно):**

Методист АЦР долго собирает программу руками. Мы сделали **студию**, чтобы быстрее получить скелет, материалы и проверку — и отдать файл дальше.

Одна фраза: **модель пишет текст — код не отдаёт программу, пока часы и правила не сошлись**.

И шутка в кармане, если шлюз капризничает: *«Модель сегодня выходной — код накинет материалы сам, только честно подпишет, что это не она»*.

Дальше — живой проход.

## 1. Что это за продукт (технически, не «про оценку»)

**Говорю:**

Продукт для методиста АЦР: **два шаблона**, часы из запроса, компетенции, план, оценочные средства, источники, **DOCX и JSON**.

Это **конвейер с правилами в коде**. Тема — вход. Жёстко: бриф неполный → **вопросы без LLM**; объём **только от методиста**; приказ и код ТФ **не генерируем**; после модели — **rebalance** и **аудит** перед файлом.

**Показ:** неполный запрос → вопросы → бриф → каркас → комплект → проверка → файл.

## 2. Главная боль — часы (развёрнуто)

**Говорю:**

Самая дорогая боль методиста при работе с ИИ — **часы**. Модель переписывает модуль — сумма по плану «плывёт». Методист тратит **полчаса-час** на поиск, где расхождение: в аттестации, в теме, в итоговой строке, в чужом файле на 248 часов, который случайно «прилип».

Мы разделили ответственность:

1. **Объём задаёт только методист** — в брифе. Слово «месяц» не становится числом. Часы из образца **не подменяют** часы из запроса (`brief_guard`, разбор файла).
2. **После каждого хода модели код пересчитывает** — `rebalance_course`: модули, аттестация внутри объёма, шаг **0,5** академических часа, план теми внутри модуля (`balance_modules`, `allocate_integer`). **Это не LLM:** пересчёт **0 токенов**, второй раз модель за часы не зовём.
3. **На экране и в аудите одна цифра** — «Часы: X из Y»; вкладка **«Проверка»** без LLM; тот же штамп в **DOCX**.
4. **Утверждение каркаса** — методист фиксирует структуру; дальше комплект не ломает паспорт часов без явной правки брифа.
5. **Стажировка 256** — отдельная логика: 254 СРС + 2 аттестации, нули в лекциях/практиках; ошибка итоговой строки из чужого образца **не копируем**.

**Кто что делает (одна фраза на схему):**  
**Методист** — объём и «утвердить». **Модель** — формулировки одним tool. **Код** — вопросы брифа, `rebalance`, аудит, DOCX.

**Как показать перерасчёт на защите:** после каркаса ткнуть сумму «X из 72»; если на `под капотом` — кадр «модель предложила 68+6» → кадр «код: 70+2=72».

Итог для методиста: не «ловить часы глазами по двадцати страницам», а **увидеть расхождение сразу** в проверке и не выгрузить файл, пока не сошлось.

## 3. Экономия токенов (развёрнуто)

**Говорю:**

Второй счёт — **токены**. Если кормить модель всей программой и всем PDF на каждый клик, счёт и время взлетают, а JSON обрывается.

Наши приёмы:

| Приём | Зачем |
| --- | --- |
| Вопросы брифа пишет **код**, не LLM | Ноль токенов, пока бриф неполный |
| Каркас **не стартует** без часов | Не жжём тысячи на выдуманную программу |
| **Один ход — один инструмент** | `update_brief`, `set_structure`, `set_lecture`… |
| В модель — **снимок шага** (`course_snapshot`), не весь курс | Короткий контекст |
| История чата **до 8 реплик**, тело **до 6000** символов | Потолок на диалог |
| Образец в промпте **обрезан**, с пометкой «не копируй тему и часы» | Меньше ввода, меньше плагиата |
| `max_tokens` **по шагу** (220–3200) | Не раздуваем ответ |
| Бюджет на задачу **25 000** токенов (`LLM_TOKEN_BUDGET`) | Стоп до бесконечного цикла |
| **Температура 0** | Меньше перегенераций «для красоты» |
| Комплект — шаг ~70 с, **без повтора**; каркас — retry на 429/5xx | Предсказуемое время и счёт |
| Аудит и выгрузка — **без модели** | Демо не зависит от шлюза в конце |

В чате после хода — **фактический расход** из ответа шлюза: методист и жюри видят цену шага.

**Как ещё уменьшить (если спросят «а дальше?»):**

| Уже в сборке | Следующий рычаг |
| --- | --- |
| 0 токенов на вопросы и на rebalance/аудит | **Кэш** утверждённого каркаса — не пересобирать структуру при правке одной лекции |
| Снимок шага, история ≤ 8, тело ≤ 6000 | **Лёгкая модель** на `update_brief` / короткие reply; тяжёлая — только `set_structure` / комплект |
| Комплект только после «Утвердить» | **Параллель модулей** только там, где нет общей квоты токенов (сейчас — последовательно, предсказуемо) |
| Бюджет 25k, max_tokens по шагу | **RAG / pgvector только по файлам методиста** — не тащить весь PDF в каждый ход (roadmap) |

Говорю коротко: *«Эргономика уже в контуре: не зовём модель, пока нечего считать; чиним часы кодом; режем контекст. Дальше режем ещё — кэшем каркаса и узким RAG, без раздувания промпта.»*

## 4. Техническая часть — коротко вслух

**Говорю:**

**Браузер** — Next.js: программа слева, чат справа, версии, кнопки брифа. Чат **не** ходит в Cloud напрямую — только в **FastAPI** (`PYTHON_AGENT_URL`), ключ на сервере.

**Python** — оркестратор `run_turn`: решает шаг, зовёт `CloudRuClient`, применяет patch, `rebalance_course`, сохраняет версию. **Аудит** — `POST /api/audit`. **Экспорт** — DOCX/PPTX/JSON на сервере.

**Данные** — SQLite локально, PostgreSQL в Docker; конфликт версий — **409**.

Подробная схема — в HTML на втором экране.
